# 连接能力（提案）

> **状态：提案，等待评审。** 本文只描述设计，不代表已经实现；评审通过后再提交实现 PR。
> 现阶段宿主提供的能力只有 `config-dirs-v1` 与 `completion-v1`，插件之间没有任何调用通道。

## 背景

备份、部署/安装这类插件都需要"连上某台 SSH 服务器"或"连上某个达梦库"。如果每个插件各存一份连接与密码：用户要配置 N 遍，凭据散落 N 份，改一次密码要改 N 处。

本文要解决的是：**连接与凭据定义一次，多个插件都能用。** 涉及的角色：

| 角色 | 谁 | 职责 |
| --- | --- | --- |
| 提供方 | `ssh`、`db` 插件 | 拥有连接与秘密；自己解密、自己建连、自己执行 |
| 消费方 | 备份、部署等插件 | 只提交"动作"，取回结果；永远拿不到秘密 |
| 中介 | `dm` 宿主 | 能力协商、依赖检查、把宿主自身路径传给插件 |

## 约束

设计必须落在既有边界内：

1. 插件是独立进程，公共契约只有参数、环境变量、标准流和退出码，不共享 Rust ABI（[插件协议](../plugins.html)）。
2. 插件拥有自己的 `config/data/cache`；宿主不读写插件数据，插件也不得在宿主 `store.sqlite3` 建表（[运行时协议](runtime-contract.html)）。
3. 能力扩展通过 `DM_PLUGIN_CAPABILITIES` 协商，不提升 `api_version`。
4. **独立进程不是权限沙箱**：插件与生命周期 hook 都以当前用户权限运行（[宿主架构](../architecture.html)）。
5. 正因为第 4 条，任何"授权"都只是声明与提示。要让共享连接真正安全，只能收窄秘密的**流动范围**，而不是指望宿主拦截。

## 核心决策：秘密不离开提供方

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| 各自持有（现状） | 每个插件存自己的连接与密钥 | 用户配置 N 遍、凭据 N 份，不满足目标 |
| 共享数据目录 | 消费方按路径读 `<home>/ssh/data` | 隐式耦合：不是稳定接口，绕过提供方的加密与迁移逻辑，提供方一改布局就崩 —— 否决 |
| 宿主托管凭据 | 连接与密钥搬到宿主 | 推翻"插件拥有自己数据"的边界，宿主成为唯一秘密持有者，攻击面更大 —— 暂不采纳 |
| 明文交付 | 提供方把密码交给消费方 | 秘密复制进 N 个插件进程，泄漏面随插件数量增长 —— 否决 |
| **代理执行** | 消费方只说"做什么"，提供方解密、建连、执行、回结果 | **推荐**：秘密始终只在提供方进程内 |

代理执行也是唯一能兼容"密钥就在提供方数据目录里、权限 0600"这一现状的做法，现有数据零迁移。

## 接口设计

### 提供方提供的机器接口

稳定、非交互、可脚本化，语义面向"动作"而不是"秘密"：

| 命令 | 语义 |
| --- | --- |
| `dm ssh exec <name> [--] <cmd> [args...]` | 在远端执行命令；stdin/stdout/stderr 直通；退出码语义见下 |
| `dm ssh copy <name> <local> <remote>` / `--download <remote> <local>` | 上传/下载文件 |
| `dm ssh describe <name> --json` | 脱敏元数据：name/host/port/username/auth_type/key_path，**不含秘密** |
| `dm db exec <name> [--json]` | 已存在（驱动待接入）；对齐同一套 stdio 与退出码语义 |
| `dm db describe <name> --json` | 与 ssh 同形（脱敏） |

已有的 `dm ssh list --json` / `dm db list --json` 继续作为"有哪些连接"的发现入口，同样不含秘密。

### 退出码约定

消费方需要区分"连接层失败"和"远端命令失败"，因此固定：

| 退出码 | 含义 |
| --- | --- |
| 远端命令的退出码 | 原样透传（含 0 与常见 1..125） |
| `255` | 提供方自身失败：连接失败、认证失败、主机密钥变化、超时、连接不存在 |

`255` 与 OpenSSH 的约定一致，便于用户和脚本沿用既有习惯。远端命令恰好返回 255 属于已知歧义，需要强区分时以 stderr 的 `错误/详情/提示` 与 `--json` 输出为准。

### 消费方如何接入

**阶段一（不新增协议，最快可用）**

1. 宿主新增环境变量 `DM_HOST_BIN`：`dm` 自身的绝对路径（现在只传 `DM_PLUGIN_HOME`，插件只能赌 `PATH` 里有 `dm`）。
2. 消费方在清单声明依赖：

   ```toml
   min_host_version = "0.5.0"
   requires = ["ssh-connections"]
   ```

3. 宿主在**启动插件之前**检查依赖：提供方是否已安装、能力版本是否匹配、`min_host_version` 是否满足。不满足就直接报错，而不是让插件跑到一半才失败。
4. 消费方调用：

   ```rust
   let dm = std::env::var("DM_HOST_BIN")?;
   let status = std::process::Command::new(dm)
       .args(["ssh", "exec", "prod", "--", "tar", "-czf", "-", "/var/lib/db"])
       .stdout(std::process::Stdio::piped())
       .status()?;
   ```

**阶段二（宿主 broker）**

消费方不再自己找 `dm`，而是通过约定的文件描述符把请求交给宿主，宿主转发给提供方；提供方流式回传结果。消费方的业务代码不用改（仍是 exec/copy 语义），只是换成 SDK 提供的小客户端。收益：宿主可以集中处理超时、并发、输出上限和调用审计，并提供方版本协商只有一处实现。

### 清单字段草案

```toml
# 消费方
requires = ["ssh-connections"]

# 提供方（阶段二，用于自声明；阶段一由宿主内置名单识别）
provides = ["ssh-connections"]
```

`dm-plugin.toml` 是 `deny_unknown_fields`：声明了新字段的清单在旧宿主上会被判为非法并拒绝安装。因此消费方与提供方都必须写 `min_host_version`，指向第一个认识该字段的宿主版本。

## 安全边界

承诺：

- 秘密只在提供方进程内解密，不写 stdout/argv/环境变量，不落临时文件。
- 消费方只能拿到脱敏元数据与命令结果。
- 提供方复用既有的主机密钥固定（`data/ssh/known_hosts`）与超时配置（`[test] connect_timeout`）。

不承诺（必须写清，避免误导）：

- **不是权限沙箱**：消费方插件同样以当前用户身份运行，可以直接读 `<DM_PLUGIN_HOME>/ssh/data`。能力声明解决的是可发现性与边界约定，不是防恶意插件；用户仍然只应安装可信来源的插件。
- 远端权限等于该 SSH 账号的权限；`dm ssh exec` 不额外提权，也不限制命令内容。
- 共享连接不等于共享审计：远端看到的仍是同一个 SSH 账号。

## 兼容与迁移

- `api_version` 保持 1；新能力走 `DM_PLUGIN_CAPABILITIES` 协商（既有约定）。
- 现有 ssh/db 数据零迁移：秘密仍在各自 `<plugin data>/` 下，密钥仍是 `.ssh-key` / `.db-key`。
- 未声明 `requires` 的插件行为不变；能力缺失时由消费方插件自行报错。
- 旧宿主不认识新清单字段，会在安装阶段报错，由 `min_host_version` 提前挡住。

## 失败形态

| 情况 | 表现 |
| --- | --- |
| 提供方未安装 | 宿主启动消费方前报错，提示 `dm install ssh` |
| 提供方能力版本不符 | 同上，按能力版本比较给出可操作提示 |
| 连接不存在 | `dm ssh exec` 退出 255，stderr 给 `错误/详情/提示` |
| 认证失败或主机密钥变化 | 退出 255，复用现有提示（`dm ssh edit`、核对 known_hosts） |
| 远端命令失败 | 退出码原样透传，stderr 是远端命令的输出 |

## 影响面

| 位置 | 变化 |
| --- | --- |
| `plugins/ssh` | 新增 `exec`/`copy`/`describe`，复用现有 `authenticate()`；测试沿用 loopback SSH 夹具 |
| `plugins/db` | 新增 `describe`；`exec` 对齐同一套 stdio 与退出码语义（驱动接入后生效） |
| 宿主 `dm` | `DM_HOST_BIN`；清单 `requires` 与启动期依赖检查；阶段二再加 broker |
| SDK | 阶段一不变；阶段二增加 broker 客户端与能力常量 |
| 文档 | 本文、[运行时协议](runtime-contract.html)、[发布与分发](publishing.html) |

## 待评审确认

1. **秘密不离开提供方插件**是否接受？若某个具体场景必须拿到秘密（例如消费方要自己维持交互式会话），需要单独设计一个风险更高的授权面。
2. 阶段一先做"消费方直接调 `dm`"，还是直接上宿主 broker？
3. 能力名先由宿主内置（`ssh-connections`、`db-connections`），还是现在就引入清单的 `provides` 自声明？
